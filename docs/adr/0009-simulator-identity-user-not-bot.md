# Feishu-Touching Test Layers Must Simulate the User as a User, Not a Bot

Status: accepted.

The Backend Smoke and IM Integration layers need an automated actor that plays the human participant in a real Feishu/Lark Thread. ADR-0006 introduced a dedicated simulator app ("customer bot") and an allowlist so its messages could drive Turns like a human's. On 2026-09-16, real-machine Backend Smoke runs (bot mode, run `run-1789557146-1be2f8` and predecessors) measured that this does not work end to end: the Bridge never receives the simulator bot's messages, so the simulated user can answer but can never drive a Turn. Decision: until the platform delivers bot-originated messages to a bot's event stream, the User Simulator and the Thread verifier in L2/L3 automation must run under a **user identity** (`user_access_token`); the `bot` Participant Mode stays implemented but is recorded as blocked by a platform delivery constraint, not by im-align code.

## Considered Options

- Keep bot mode and fix im-align: rejected as stated — the failure is upstream of im-align. A probe on the Bridge app's long-connection stream confirmed the platform does not push other bots' messages to `im.message.receive_v1` at all, even when the message mentions the receiving bot; nothing the Bridge filters or allowlists can act on events that never arrive.
- Bot mode plus sensitive scope `im:message.group_at_msg.include_bot:readonly`: recorded in ADR-0006 as the platform's own documented condition for receiving bot messages. Not pursued: it is a sensitive scope on the production-facing Bridge app, it widens what group bot chatter the Bridge must process, and it was not validated to cover bot-originated (as opposed to bot-mentioned) traffic.
- User identity via `user_access_token` (chosen): user-originated messages are delivered to the Bridge's event stream reliably (measured across all historical real-machine runs and re-confirmed by run `run-1789559578-12acce`: reply → emoji ack → Turn 2 in one poll cycle). The cost is credential custody: a test user's OAuth grant must be bootstrapped interactively. Local runs extract a fresh access token from an authorized CLI's local credential store. CI stores the longer-lived rotating refresh token (`IM_ALIGN_E2E_FEISHU_USER_REFRESH_TOKEN`), exchanges it immediately before each serialized Feishu job, and persists the replacement refresh token through a repository-scoped secret-writer credential; it does not store the roughly two-hour access token.
- Bot mode as the verifier/polling identity only, user mode for driving Turns: kept as a building block — the simulator app's tenant token (with `im:message.group_msg`) reads the Thread well; what it cannot do is make its own messages reach the Bridge.

## Measured platform constraints behind this decision (2026-09-16)

- **Event delivery**: bot-originated group messages never arrive on another app's `im.message.receive_v1` long connection. Symptoms in runs: `participant_replied: true` (the OpenAPI listing sees the reply) but `participant_reply_acked: false` and `participant_drove_turn: false` (the Bridge event stream never sees it).
- **Message listing**: the chat-container listing (`container_id_type=chat`) returns zero thread replies for a bot identity — 50/50 top-level texts, none with `root_id`. Thread replies are only visible through `container_id_type=thread` with the root message's `thread_id` field (`omt_...`); passing the root message id is rejected with `230001 invalid container_id`. Both the polling transport and the Thread verifier resolve the root's `thread_id` once and then list the thread container.
- **Card patching**: the Bridge patches each Turn's result into the Turn-start thinking card in place. Dedup by `message_id` alone therefore hides every Agent answer from a poller that already saw the "Agent Is Thinking" card; freshness must key on `update_time` (`select_fresh` in `tests/e2e/transports.py`).
- **HTTP timeouts**: the simulator/evaluator LLM endpoint (ark plan gateway, `doubao-seed-evolving`) intermittently keeps a connection alive without ever finishing the response — measured twice as a hang of 10+ minutes inside `SSL_read`, once while reading response headers. Per-operation socket timeouts do not fire because the connection is never silent long enough. The LLM client (`post_json_with_deadline`) enforces a cumulative deadline over the whole exchange (connect, handshake, headers, body) with each `recv` limited to the remaining time.
- **Skill closure**: the pinned bundle's entry skill `grill-with-docs` only forwards to `grilling` and `domain-modeling`; without installing the transitive closure the Agent cannot load its own entry skill.

## Consequences

- `as-user` is the supported Participant Mode for Backend Smoke / Full e2e / IM Integration until bot-to-bot event delivery is available and re-validated; `--participant-mode bot` remains selectable but a run that uses it is expected to fail at `participant_reply_acked` / `participant_drove_turn`.
- The User Simulator transport and `FeishuOpenAPIVerifier` must be built from a Participant identity, never the Bridge credentials: the Bridge app intentionally lacks `im:message.group_msg` (denied with `230027` when read is attempted). Bot mode uses the simulator app's credentials; as-user mode uses `user_access_token`. The simulator token can also read message reactions; the Bridge token cannot (`99991672`).
- CI must never use a static user access-token secret. Each Feishu-touching job exchanges `IM_ALIGN_E2E_FEISHU_USER_REFRESH_TOKEN`, masks the generated pair, retries persistence of the returned replacement before testing, and exposes the fresh access token only to later steps in that job. Credential-writer secrets may execute only trusted `main` code. Refresh and test execution share the existing single-session concurrency group because refresh tokens rotate on use; exhausted persistence retries require a new interactive grant.
- Re-enabling bot mode requires: (a) platform delivery of bot-originated messages to the Bridge's event stream, re-probed on the Bridge app long connection, and (b) re-running the Backend Smoke matrix in bot mode to green. Until then the allowlist in ADR-0006 stays as defense-in-depth and as the documented extension point.
- ADR-0006 remains the record of the allowlist design; its delivery constraint bullet and this ADR together supersede the assumption that an allowlisted bot can play the customer in CI.
